## 概要

Bradesco のクラウド移行を題材に、依存関係の発見から移行波の設計、Java アプリの改修、検証までをエージェントと人が分担する方法を紹介します。

- オンプレミスと Azure の間をプロキシで個別移行した結果、循環依存や再試行、遅延が発生。OpenShift、サービス台帳、Dynatrace、GitHub などを基に依存関係を可視化し、呼び出し・データ・統合先の近さで自己完結した移行波を組みます。
- 社内の modernization-kit はスライド上、31 エージェント、34 スキル、6 フック、6 MCP を組み合わせ、評価→仕様→計画→実装→検証を進めます。対象範囲、業務要件、残余リスク、環境への昇格は人が判断します。
- **デモ:** 架空の予約アプリの Java 8／Spring Boot 1 を評価し、Log4j などの問題を確認。事前に用意した修正ブランチで Java 21 と新しい Spring に移した結果を見せます。実データベースを使った本番移行のデモではありません。
- 手作業で約2日かかる1サービスの仕様作成と実装について、測定した実サービスでは計33〜44分と報告。これは特定の測定条件であり、全サービスの移行時間や保証値ではありません。約1,000サービスの初期対象に対する調査・計画は4週間、6〜8か月のプログラムでの改修約50%加速は**見込み**です。
- データ移行は難所で、レプリケーション、カナリア展開、切り替え時の遅延・停止への対策が必要。IBM MQ は複雑化を避けて ARO 内に残し、DB2／メインフレームも当面オンプレミスに残す構成です。
- Azure Catalyst は Ignite で発表、Azure Resource Manager MCP Server はスライドでパブリックプレビューと明記されています。
