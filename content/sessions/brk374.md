## 概要

Sitecore の事例から Azure Managed Redis をキャッシュや AKS 上のアプリに利用し、性能と拡張性を高める方法を紹介します。

## セッションの内容

前半は Azure Managed Redis のユースケースを整理し、Sitecore Content Hub の実例を掘り下げました。Sitecore の登壇者は、Content Hub がデジタル資産のメタデータ、関係性、承認・配布のワークフローを扱い、AKS 上で動作すると説明。構成図では、Blob Storage が原本・派生ファイル、Redis が資産エンティティと関係性、Elasticsearch が検索用の非正規化データを担い、AKS のワーカーがバックグラウンド処理を行います。したがって、この事例の Redis は単なる破棄可能なキャッシュではありません。

Redis の役割は三つです。第一に、ハッシュとセットで資産や製品のエンティティと相互参照を表現するデータ層。第二に、検索インデックスの再構築など、大量のデータを読み出す処理を支える低遅延・高スループット層。第三に、資産の取り込み、メタデータ付与、画像の派生版生成などの作業を優先度付きで配るメッセージブローカーです。最後の用途では Sorted Set に優先度を持つ作業を格納し、AKS ワーカーが優先順に処理します。キューの未処理数をアプリケーションメトリックとして公開し、KEDA でワーカーポッド数を水平スケールする仕組みも説明されました（Redis 自体をこの指標でスケールする話ではありません）。Sitecore 側は、マネージド運用で日常保守の負担が減り、2人分の運用リソースを顧客対応・製品改善に振り向けられたこと、Entra ID のマネージド ID とプライベートエンドポイントを採用したことを紹介しました。これらは登壇企業の事例・報告です。

後半は、データベースを正本とする小売サイトを想定し、Redis を追加する前にクエリ・インデックス・データベース設定を見直し、必要なら集計結果を事前計算するよう勧めたうえで、五つのキャッシュパターンをデモしました。キャッシュアサイドはミス時に DB から取得し TTL 付きで保存、参照データの先読みはカテゴリのような安定データを起動時にキャッシュ、ライトスルーは価格変更を DB とキャッシュへ反映、ライトビハインドはページビューカウンターを Redis に集約して定期バッチで DB に書き込みます。イベント駆動更新では、Azure SQL の変更追跡と Azure Functions を使い、別システムからの在庫変更を検出してキャッシュを無効化・更新します。

要点は、外部キャッシュを足す価値があるほど同じ結果が再利用されるか、鮮度・TTL・無効化をどう設計するか、そしてメモリ不足時の退避、接続切断、タイムアウト、再試行、同時ミスなど「正常系以外」も試験することです。複数サービスにまたがる更新には分散トランザクションの保証がないため、整合性とエラー処理も必要です。パターンを機械的に当てはめるのでなく、データの性質と業務要件に合わせるよう強調しました。新機能のスライドでは Azure Managed Redis 8 と Agent Kit が Public Preview、データベース連携ガイダンス、移行ツール、カスタムアクセスポリシー、Keyspace notifications などが GA と表示されていました。これはスライド記載の収録時点の区分です。
