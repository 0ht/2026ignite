## 概要

Azure の移行支援を用いて資産を発見し、事業上の根拠、移行計画、設計と実行を結び付ける方法を説明します。

## セッションの内容

- **銀行の移行事例**：Aldermore は老朽化した8拠点の集約と並行し、規制・業務報告を支える100 TB超のデータ基盤を Azure に移行した。Azure Migrate で発見・評価し、Storage Mover で実データを使ったリハーサルと切り替えを行い、Chaos Studio で障害時の回復を検証した。登壇者によると、移行後は夜間バッチが従来より約2〜3時間早く終わり、遅延や障害からの回復余地が生まれた。
- **資産から意思決定へ**：Azure Catalyst はサーバー一覧に加え、ServiceNow CMDB や監視データを取り込み、依存関係を基にワークロードをアプリ単位にまとめる。デモでは重要度・複雑度を付け、移行先、セキュリティ上の課題、移行ウェーブを含む提案書を作成した。Azure Value Uplift はコスト削減だけでなく、回復性・俊敏性・生産性も比較材料にする。
- **設計とウェーブ計画**：CAF・WAF に沿うプラットフォームランディングゾーンと、700超の参照アーキテクチャを基にしたアプリ設計を提案する。架空の製薬企業のデモでは、.NET アプリの App Service と Azure SQL、Java・Oracle アプリの AKS と PostgreSQL への移行先を例示。依存関係、準備状況、重要度、工数に基づくウェーブを担当者が確認・修正・承認する。
- **実行と統制**：承認済み計画からデータベースやファイル共有の移行状況を追跡し、開発者は GitHub Copilot 側でコード・依存関係を評価してフレームワークやクラウド設定を更新する。アプリとデータベースの連携評価はプレビュー、組織標準を計画に反映する rulebook は一般提供と説明された。コード変更、ビルド、テストは人が確認する。
- **質疑で示された制約**：既存のランディングゾーンを前提とした設計は今後対応する予定で、当時は新規環境向け。生成された Terraform をダウンロードして編集できるが、編集後の再アップロードは未対応と説明された。依存関係の発見はオフライン collector や既存の監視データでも可能だが、取得できる詳細度は付与する権限に左右される。
