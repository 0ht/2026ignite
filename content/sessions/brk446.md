## 概要

データ所在地や接続断への備えを背景に、Azure の公開クラウドと別環境の間でアプリを移植できる設計を検討します。

## セッションの内容

### 「同じアプリを別環境でも動かす」設計パターン

規制産業・公共部門・エッジ環境では、データ所在地や接続断への備えが調達条件になりつつある一方、Azure と他環境のサービスが完全に同等になるのを待つことも、全環境で共通する最小機能だけを使うことも現実的でない、と講演者は整理します。そこで提示する Adaptive Apps は製品フレームワークではなく、アプリのコードを環境固有のサービスから切り離して配備時に適応させる設計パターンです。Azure を含む既存基盤の能力を隠すランタイムやサイドカーを必須にせず、段階導入でき、Azure で優れた体験を保ちながら他環境への移行経路も残すことを原則とします。

具体的には Radius のリソースモデルで、アプリが必要とする ingress、service、database などを宣言し、各環境の recipe が実体を割り当てます。例では Azure 側を Front Door、AKS、Cosmos DB などで構成し、別環境では Gateway API、Kubernetes、PostgreSQL などに置き換えます。これはアプリのデータプレーンを一律に抽象化するというより、配備時の管理プレーンで資源を解決する仕組みです。アプリ側は MQTT や OIDC など選んだプロトコルを使い、個々の基盤機能まで同一になることは前提にしません。

### エッジでの ID・AI とデモ

多層構成の例では、Azure の AKS と Arc 対応 Kubernetes、Radius、必要に応じた Dapr、ローカル推論用 Kaito、Entra ID と Keycloak、OpenTelemetry/Azure Monitor、Arc 拡張による配布・更新を組み合わせます。Keycloak をアプリ側のローカル ID プロバイダーとして置き、接続中は Entra ID やローカル AD とフェデレーションし、切断中も新規認証を含む認証基盤を動かせる考え方を説明しました。株取引サンプルのデモでは、クラウド版は Event Grid や Foundry 等、ラップトップ上の Kubernetes 版は Mosquitto MQTT、Keycloak、Kaito のローカルモデルを使い分け、同じアプリを異なる環境へ配置しました。

後半では Adaptive Apps の考え方をエージェントにも広げます。エージェントの ID と接続を扱う Agent Gateway、複雑な要求は大規模モデル、単純な要求は小型・ローカルモデルへ振り分ける AI Gateway/Router、Kubernetes 上の Kaito、OpenTelemetry、OPA と Agent Governance Toolkit などを構成要素として挙げ、モデルやエージェント・フレームワークを固定しない方向を示しました。将来像として、実行環境をまたぐエージェントの移植性も述べています。

### 切断時の記憶とガバナンス

ポータブル・メモリのデモでは、クラウド側エージェントの会話記憶を PostgreSQL に保存し、ローカル環境へ同期して、クラウド接続を失っても同じ文脈を使って会話を継続しました。同期はまず一方向にし、クラウドを唯一の更新元、ローカル側を読み取り専用にすることで、双方向同期の競合を避ける設計例です（同期機能自体を Adaptive Apps のツールチェーンが提供するわけではなく、データ基盤ごとの機能を使うと説明）。

エンタープライズのエージェント統制案としては、クラウドで定期発行する暗号化済みの利用許可枠（grant）を、切断中のローカルエージェントが検証し、枠内でのみ業務を続ける方式を提案しました。上限超過時は要求を拒否し、活動を改ざん困難な台帳へ記録します。100体のエージェントが通信断やクラッシュを起こすピザ製造デモで、各エージェントに金額ベースの枠を適用し、再接続後に処理を同期する様子を示しました。これは講演者自身が初期段階の概念実証として紹介したもので、完成済みの製品機能とは区別されています。
