## 概要

Azure Local 上の SQL Server とローカル AI を組み合わせ、データ主権や低遅延が必要な環境でアプリを構築します。

## セッションの内容

### Azure Local 上に閉じたアプリケーション

Bob Ward は、クラウド移行を急がない組織、クラウドへ移る前にオンプレミスを近代化したい組織、Azure 利用中でも一時的な退避先を求める組織を例に、Azure Local を「Azure と整合した管理体験をオンプレミスで使う基盤」として説明しました。Azure Arc 接続型だけでなく、インターネットから切り離したエアギャップ構成も選択肢です。紹介した医療機関のサンプルは実運用向け認証済み医療製品ではなく、患者の受け入れ情報を扱うデモ用アプリです。Azure Virtual Desktop 上のブラウザー、Azure Local の VM 上の SQL Server 2025、別の AKS クラスター上の Foundry Local とローカル AI モデルで構成し、患者データや推論を施設内にとどめます。Azure 公開クラウド接続は例では管理用途であり、データや推論に必須ではないと説明しました。

### SQL Server 内でのローカル検索と RAG

デモでは、救急隊員の自由記述から SQL Server の正規表現機能で症状などの信号を抽出し、JSON データとして扱います。Foundry Local の埋め込みモデルで患者履歴のベクトルを事前生成し、SQL Server 2025 のベクトル検索で「胸の中央が締め付けられる」といった自然文から、異なる表現で記録された胸部圧迫感の履歴を探す流れを示しました。検索は T-SQL のストアドプロシージャから行い、埋め込み生成と検索を分けて、推論モデルの呼び出しや類似検索の処理をアプリ側に持ち出さない構成です。

受入れ時のブリーフィングでは、患者情報、履歴検索の結果、施設の指示を SQL Server 内でまとめ、REST 経由でローカルのチャットモデルへ渡して RAG による提案を生成します。モデルは当該患者情報を事前学習で知っているわけではなく、検索した情報を文脈として追加する方式です。アプリにはストアドプロシージャの結果を返し、SQL Server の権限モデルで AI 呼び出しを制御します。デモでは医療従事者が最終判断する前提も明示されました。

AI 呼び出しの監査には SQL Server の append-only Ledger テーブルを使い、モデルとの要求・応答、プロンプト等を改ざん検知可能な記録として残す例を紹介しました。さらに、同じローカルモデルを SSMS の GitHub Copilot 機能によるデッドロック解析や、VS Code の Copilot と SQL 拡張によるスキーマの説明にも利用し、データベース運用・開発者がクラウドにデータを送らずに AI 支援を使う構成を実演しました。

### 接続型・切断型と移行の選択肢

Azure Local は Azure に接続した構成なら Arc を介した管理や従量課金を使え、切断型ではローカルのリソース管理を行いますが、一部の機能やライセンス上の条件は異なると説明しました。Foundry Local のモデルにも個別ライセンスが必要な場合があります。講演では、同じアプリと SQL を Azure SQL Hyperscale／クラウド側 Foundry に移す場合や、Azure からオンプレミスへ戻す場合にも、モデルのエンドポイント等を切り替えて継続できる構成を示しました。つまり「クラウド不要」はクラウドへ移れないという意味ではなく、規制・接続性に応じてローカル運用し、必要なら移行できる橋渡しを指しています。
