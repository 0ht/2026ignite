# BRK280: Designing an agent harness that orchestrates models

Copilot Fusion を例に、タスクごとのモデル選択や複数モデルの協調と、品質・速度・費用のトレードオフを説明します。

## 概要

Copilot Fusion を例に、タスクの性質、モデルの強み、推論量、キャッシュと費用を考慮して、1つまたは複数のモデルを協調させるハーネスを解説します。

- Standard は1プロンプトにつき1モデル、High は複数モデルの協調、Max は難しい課題向けの強いモデルを使うと説明。Single、効率的なモデルの下書きを判定して必要時に強いモデルへ移す Cascade、別系統のモデルが並列でレビューする Critique を紹介します。
- モデルを替えると既存のプロンプトキャッシュを失い、安価なモデルでも長い会話の再処理費用が増える場合があります。コンテキスト長の小さなモデルへの切り替えは圧縮も必要になるため、品質・遅延・キャッシュ有効期限を一緒に考慮します。
- **デモ:** 同じサンフランシスコのベーカリー巡りサイトを Opus 5.5 High と Fusion High で生成。登壇者はそれぞれ70 AI credits と8 AI credits と報告しました。これは1回の例で、品質評価は登壇者の主観であり、すべての課題で同じ差になる保証ではありません。
- 登壇者は Terminal-Bench 4.1 で Fusion Max の解決率71.2%、比較対象65.8%、Fable 5.2 比で費用88%減と報告。特定のベンチマーク・条件における測定であり、実業務の品質や費用を保証する数字ではありません。
- Fusion は10月28日に GA と説明。管理者のモデル制限を尊重し、当時11月30日までルーティングされたモデルに30%割引を適用。独自モデルや独自 API キーの持ち込みは将来の構想です。
