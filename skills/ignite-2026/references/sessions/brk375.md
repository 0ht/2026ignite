# BRK375: Migrate and modernize MongoDB applications with Azure DocumentDB

MongoDB アプリを Azure DocumentDB へ移行する際の互換性評価、データ移行、動作検証と運用を説明します。

## 概要

MongoDB アプリを Azure DocumentDB へ移行する際の互換性評価、データ移行、動作検証と運用を説明します。

## セッションの内容

Azure DocumentDB を MongoDB 互換のマネージドサービスとして紹介し、移行時の評価・データ転送だけでなく、移行先の設計や切り替え後の運用まで扱いました。製品説明に続いて、規模も移行理由も異なる二社の経験を比較し、最後に VS Code から移行を構成・監視するデモを行っています。

AB InBev の事例では、数百に及ぶクラスター（登壇者は500以上と説明）、数十TB級から約100TBに近い大規模データを対象にしました。多数の移行を並行させながら、稼働中のソースに過剰な負荷をかけず、移行先の一時的な過剰プロビジョニングも避ける必要がありました。発表では、カスタムスキーマ移行、コレクション配置、サイズの異なるクラスターへの対応、進捗・失敗の可視化が改善点として挙げられました。顧客は本番切替後も約4か月にわたり二重書き込みを続け、旧環境を残して検証する長期移行を実施したと報告しています。

Abercrombie & Fitch の Digital Product Hub は、社内の商品・在庫・価格情報を統合し、ベンダー向けフィードを生成する仕組みです。約900件の日次ジョブを処理する同チームは、RU ベースの Cosmos DB for MongoDB vCore で、定時に重なるフィードによる RU スロットリング、再試行・失敗、ピーク用キャパシティのコスト、検索フィルターに合う複合インデックスの制約を課題として挙げました。CPU・メモリ・ストレージに基づくより予測しやすい費用と、フィルターに合わせたインデックス、コンピュート階層の調整が移行先を選ぶ理由でした。移行は全量コピー後に変更ストリームで追随し、読み取り専用テスト、読み取りアプリ、書き込みアプリ、コンシューマーの順で段階的に切り替え、主なアプリ変更は接続先の更新と再起動だったとのことです。ワイルドカードインデックスの差異で CPU が上がった際は、対象クエリ向けのインデックスを追加して対処しました。顧客報告では、QA と本番を合わせた年間 TCO が約75%減、フィード処理時間が19.5%短縮し、スロットリング由来のエラーは数千件からほぼゼロになりました。これらの数値は同社のワークロードに関する事例値で、一般的な移行効果を保証するものではありません。

移行ツールのデモでは、VS Code 拡張からソースとターゲットを選び、オンライン移行ジョブを Azure 上に作成し、移行対象やシャーディング方針を選択、進捗を監視して完了後に切り替える流れを紹介しました。ローカル PC が大規模転送を担うのではなく、拡張から開始する Azure の移行サービスとして説明されています。セッション後半では、短時間での小規模クラスター作成、統合検索・ベクトル検索、データベース／コレクション単位の RBAC、分散コーディネーターなども発表項目として挙げられました。これらは当日の発表・プレビュー状況として扱い、現在の一般提供やロードマップの確定とは区別してください。
