## 概要

AI の学習や推論を支える Azure Storage について、大規模データ、性能、セキュリティを含む設計を紹介します。

## セッションの内容

- **ワークロード別の要件**：学習・追加学習では大規模データの読み込みとチェックポイント書き込みの容量・スループットが重要。一方、推論では企業データの鮮度とアクセス制御、エージェントでは低遅延の状態保存・復元、バージョン管理、監査ログの不変性が重要になる。Blob、Managed Lustre、ファイル／ディスクを用途に応じて使い分ける。
- **学習向けストレージ**：Azure Managed Lustre は並列ファイルシステムをマネージドで提供し、Blob とのデータの入出力に対応する。資料では AMLFS Plus の一般提供と、単一名前空間で最大120 PiB・2.5 TB/s を紹介した。必要な容量や帯域、ワークロードの特性を踏まえて選ぶ。
- **Blob Turbo Tier**：プレビューの SSD ベース階層を既存の階層と同一アカウント・名前空間で使い、Smart Placement がアクセスに応じてデータを移動する。デモでは Turbo に置く目標割合を設定し、データ配置を管理する流れを説明した。資料の「74%低コスト」は10 PiBのうち20%を Turbo に置いた特定のモデル比較であり、すべての構成に適用される保証ではない。
- **データ転送とキャッシュ**：Blob over RDMA は REST を制御経路に残し、データを RDMA で GPU メモリなどへ転送する方式として NVIDIA cuObject との連携を紹介。BlobFuse はファイルシステム風のアクセスとノード内キャッシュを提供し、DACS は各ノードの NVMe を共有キャッシュとして、モデル重みを他のワーカーが再利用できるようにする。Blob は永続的な正本のまま、キャッシュは一時的なものとして扱う。
- **エージェントの状態と安全性**：共有 KV キャッシュを再利用すれば同じコンテキストの GPU 再計算を減らせる。Blob を LangChain Deep Agents の永続ワークスペースや Azure Container Apps Sandboxes のマウント先として利用し、途中成果や記憶の保存・復元を行う例を紹介した。アクセスを限定する identity に結び付いた user delegation SAS、短時間の session-based authentication、ログの不変化・階層化も説明した。
- **データ管理**：Blob access points はパートナー側のデータを移行・複製せず Blob API で読み取る仕組みとして紹介され、公開エンドポイントは一般提供、プライベートネットワークはプレビューとされた。Storage Discovery で容量や最終アクセスを分析し、Storage Actions の mock run で変更対象を事前確認してから処理する。
