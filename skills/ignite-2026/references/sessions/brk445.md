## 概要

Azure と利用者の責任分担を踏まえ、可用性の目標、設計、構成、テストを通じた回復性の確保を説明します。

## セッションの内容

### 回復性を事業要件として設計する

回復性は、冗長な部品を置くだけでは保証されません。業務上許容できる復旧時間・データ損失（RTO/RPO）を先に定め、Microsoft が担うプラットフォームの安全な変更・障害封じ込め・復旧連絡と、利用者が担うサービス選定・独立した障害経路・容量・データ保護を組み合わせ、エンドツーエンドで復旧を実証する、という責任分担を冒頭で確認します。移行時に回復性を後回しにすると、後からの再設計が高くつく点も強調されました。

Microsoft 側の課題として、2026年9月30日の ExpressRoute 障害では更新の集中と準備完了判定の不具合が重なり、復旧に約30分かかったこと、同年10月30日の緊急パッチでは利用者のメンテナンス時間帯を迂回したうえ通知も不足したことを説明しています。一方、利用者側の設計例として、2024年のシカゴ接続拠点障害では異なる拠点へ回線を分散すること、2025年の Azure Front Door 障害では Traffic Manager と別の入口をフォールバックにすることを挙げ、同じ障害でも経路の多様化と切替訓練が影響を分けたと述べます。

### ゾーン障害を封じ込め、ワークロードを戻す

ゾーン冗長化では VM だけでなく、ディスク、NIC、IP、ロードバランサーなど依存リソースも配置をそろえる必要があります。スライドでは、VM Scale Sets Flexible によるゾーン間・ゾーン内 fault domain への分散、ディスク単位で影響を分ける仕組み、ExpressRoute Resiliency Guard、Multicloud Interconnect などを回復性の構成要素として紹介しました。Multicloud Interconnect は AWS 向け一般提供、GCP 向けパブリックプレビューとして発表され、異なる2拠点・4経路を使う接続をデモしました。発表時点のプレビュー機能である VM Zone Resilience のデモでは、障害ゾーンのデータベース VM を ZRS ディスクとともに正常なゾーンへ戻し、VM の ARM ID・IP・ネットワーク設定を保ったまま約2分で注文処理を再開し、障害前に確定した注文が残ることを示しました（利用可能なリージョン・SKUには制約があります）。

リージョン障害には二つの道筋を示します。Azure Site Recovery（ASR）は VM の複製・復旧計画・非本番テストを担い、性能ディスク、NVMe、Azure Local から Azure への経路など対応範囲の拡張も紹介します。これに対し、自社で復旧を組む場合は「データを守る→コンピュートを起動する→通信を戻す」の順に依存関係を設計します。Azure Files のリージョン間コピー、Elastic SAN のスナップショット、Azure Backup や専門 BCDR パートナーをデータ保護の選択肢として挙げ、Front Door の正常性ベース切替や地理的に分散した ExpressRoute を復旧先へ事前接続しておくよう促しました。

### 測定・訓練・証跡を一つの運用にする

発表された Azure Infrastructure Resiliency Manager は、アプリケーション単位の依存関係と RTO/RPO、リスク、推奨修正、復旧ドリルをまとめ、復旧可能性の証拠を残す方向性として紹介されました。Resiliency Agent は新規構成に対するテンプレート提案、既存環境の評価と修正案、構成ドリフトの検知を支援するデモで説明されています。Chaos Studio のシナリオでは、ゾーン停止だけでなく CPU・メモリ圧迫、イベント駆動メッセージング障害、データベース切替や DNS/Entra の依存障害を模擬します。ASR のテストフェールオーバーは本番と隔離したネットワークで実施し、技術確認と業務確認の後にテスト資源を片付け、達成した RTO/RPO と調査結果を記録する流れでした。
