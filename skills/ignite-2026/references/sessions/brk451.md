## 概要

AI 支援の評価や変換ツールを使い、Oracle から PostgreSQL への移行とデータ移行の手順を整理します。

## セッションの内容

### PostgreSQL から PostgreSQL への移行

講演は、データベース移行をデータのコピーだけでなく、互換性確認・アプリ切替・業務上の判断を含む作業として扱います。Azure HorizonDB をターゲットにする例では、既存の PostgreSQL（オンプレミス、Azure VM、他クラウド等）から Azure Database Migration Service（DMS）を使う同種移行を紹介しました。計画停止が許容できる場合はオフライン移行、サービスを継続する場合は初期コピー後に変更データキャプチャ（CDC）で差分を追随させ、同期を確認してから切り替えるオンライン移行を選びます。デモでは接続先と対象 DB を設定し、互換性検証、スキーマ・データの初期ロード、追加行の CDC 反映を確認してアプリの接続先を変更しました。DMS のリージョン提供状況は拡大中なので、移行先を決める前に対象リージョンを確認するよう説明しています。接続には送信元での許可 IP 設定によるパブリック経路、または ExpressRoute/VPN とプライベートエンドポイントを使う構成が示されました。

### Oracle のスキーマ・アプリ・データを分けて移す

Oracle 移行では、スキーマと PL/SQL、Oracle 固有のアプリケーション依存、データを三つの柱として分け、それぞれに適した作業と検証を行います。VS Code の Microsoft PostgreSQL 拡張で Oracle の DDL を抽出し、Microsoft Foundry の AI 支援で PostgreSQL 向けに変換、検証用データベースでコンパイル確認します。オブジェクトエクスプローラーや HTML レポートで変換・未変換の差分と理由を調べ、必要箇所を人が修正してからデプロイする手順です。デモでは22オブジェクトが対象となり、そのサンプルでは全件が変換されたと報告されましたが、これは当該デモの結果であり、任意の Oracle スキーマで完全変換できる保証ではありません。

アプリケーション側は、GitHub Copilot CLI のスキルが SQL、ドライバー、ORM（例: Hibernate）等の Oracle 依存を調べ、Java、.NET、Python、C/C++ のコードを PostgreSQL 向けに評価・変換・検証する構想を示しました。ビルドとテストを繰り返し、Docker 上の使い捨て PostgreSQL を使った統合テストや差分・レポートを人がレビューする流れが紹介されています。最後に DMS でデータを移し、スキーマ変換やアプリ変更とは別工程として確認します。講演時点では Oracle 19c 以降を対象にした DMS の Oracle→HorizonDB 移行はオフライン方式で、TLS 接続とテーブル単位の進捗監視が説明されました。

### First Advantage の移行例と実務上の判断

First Advantage は、国際事業の業務アプリ GCM を、オンプレミスの Oracle から Azure Database for PostgreSQL へ移行した事例を共有しました。事前評価でスキーマや PL/SQL の障害要因を洗い出し、AI 変換案を DBA が確認・テストしたうえで、CDC により移行中も両 DB の変更を同期し、業務確認後に停止時間をほぼゼロに近づけて切り替えたと説明しています。顧客登壇者によると、このアプリは同社の Oracle ライセンス費用全体の約12%に相当し、AI 支援を含む移行では、当初複数四半期と見込んだ作業を約1四半期で完了しました。次の5アプリは評価済みで、2027年Q2を次の本番移行目標として挙げています。事例の移行先は Azure Database for PostgreSQL であり、講演の製品デモの移行先 HorizonDB とは区別されています。

最後に、VS Code 拡張によるスキーマ変換、Copilot CLI によるアプリコード変換、DMS によるデータ移行を別々の役割として整理し、対象リージョン・ネットワーク・互換性・切替方式を確認してから段階的に進めるよう案内しました。
