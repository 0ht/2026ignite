## 概要

Azure の障害事例と顧客事例を基に、依存関係の把握、復旧、バックアップ、AI を活用した回復性の改善を扱います。

## セッションの内容

Mark Russinovich は、2014 年の Azure Storage 障害を振り返り、小さなコード変更が共有コードパスのゼロ長 Blob 読み取りで無限ループを起こし、再試行を通じて障害が広がった経緯を説明します。この教訓から、変更を段階的に展開し各段階で監視する Safe Deployment Policy を導入したこと、顧客が実際に経験する成功率やスループットを共通の SLI/SLO として計測し、逸脱を検知することを重視します。クラウド側が担う基盤・ゾーンの耐障害性と、顧客側が設計するアプリケーション、リージョン間復旧、データ保護を区別し、リージョンや可用性ゾーンにリソースを置くだけでは自動的に別の場所へ復旧しない点も強調しました。

続いて Azure の回復性機能を、設計時の「Start resilient」、既存環境の把握・改善を行う「Get resilient」、訓練と復旧準備を続ける「Stay resilient」の流れで紹介します。Resiliency Agent は構成図からリソースを識別し、ゾーン冗長化の設定案と Bicep、Terraform、ARM の IaC を作成します。Azure Infrastructure Resiliency Manager ではリソース間の依存関係を基に Service Group を作り、重要度や目標に応じて単一障害点、推奨対策、コストや停止影響を評価し、SLI やドリルの結果をレポートできます。データ保護では、ペアリージョンに限らず選択したリージョンにバックアップ保管庫を置き、別リージョンへの復元を行う例を示しました。サイバー復旧については、論理的なエアギャップ、不変性、ソフト削除、複数ユーザー認証、暗号化に加え、テナントが利用不能になった場合の別テナントへの復元を説明しています。

Banco Santander の Enrique González Bejarano は、設計段階から複数ゾーンを使い、規制対象のデータ保管と最長 10 年の保持要件を踏まえてバックアップを整え、定期的なゾーン停止ドリルで稼働を確かめていると話しました。リージョン選択バックアップを試行し、Azure Data Lake のネイティブバックアップや、運用中の構成変化を把握する Azure Infrastructure Resiliency Manager も評価中だと紹介しています。講演の結論は、回復性を後付けの作業にせず、測定・訓練・復元確認を継続する運用として設計し、AI エージェントはその分析や IaC 作成を支援する手段として使う、というものです。
